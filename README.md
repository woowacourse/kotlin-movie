# 3 단계 - 영화 예매(DB)

## 데이터베이스 관련 기능 목록
- [x] 애플리케이션 시작 시 데이터베이스 연결을 생성한다.
- [x] 로컬 실행 환경에서는 파일 기반 H2 데이터베이스를 사용한다.
- [x] 테스트 환경에서는 In-Memory H2 데이터베이스를 사용한다.
- [x] 데이터베이스 초기화 시 필요한 테이블을 생성한다.
- [x] 영화 정보를 데이터베이스에 저장한다.
- [x] 상영관 정보를 데이터베이스에 저장한다.
- [x] 상영 일정을 데이터베이스에 저장한다.
- [x] 예매 정보를 데이터베이스에 저장한다.
- [x] 애플리케이션 재실행 시 저장된 영화 및 상영 정보를 다시 조회한다.
- [x] 애플리케이션 재실행 시 저장된 예매 정보를 반영해 좌석 예약 상태를 복원한다.
- [x] 최초 실행 시 상영 정보가 비어 있으면 기본 데이터를 seed 한다.
- [x] 결제 확정 이후에만 예매 정보를 데이터베이스에 저장한다.

## 데이터베이스 테스트 목록
- [x] H2 데이터베이스 연결이 정상적으로 생성된다.
- [x] 테이블 초기화가 정상적으로 수행된다.
- [x] 기본 상영 데이터를 저장한 뒤 다시 조회할 수 있다.
- [x] 예매 정보를 저장한 뒤 다시 조회할 수 있다.
- [x] 저장된 예매 정보가 좌석 예약 상태에 반영된다.
- [x] 테스트 간 데이터가 서로 영향을 주지 않는다.

## 구현 전략
### 1. 저장 대상
- 상영 정보와 예매 정보를 데이터베이스에 저장한다.
- 좌석 배치는 고정 규칙으로 관리하고, 좌석 자체를 테이블로 따로 저장하지 않는다.
- 실제 영속 대상은 `Movie`, `Screen`, `ScreeningSchedule`, `ReservationInfo`에 필요한 정보다.

### 2. 스키마 구성
- `movies`: 영화 ID, 제목, 러닝타임
- `screens`: 상영관 ID
- `screenings`: 상영 ID, 영화 ID, 상영관 ID, 시작 시각
- `reservations`: 예매 ID, 상영 ID, 좌석 행, 좌석 열

### 3. 도메인 복원 방식
- 데이터베이스 조회 결과를 바로 비즈니스 로직에 넘기지 않고, 도메인 객체로 다시 조립한다.
- 좌석은 고정 좌석 템플릿을 기준으로 생성하고, 예매된 좌석만 `RESERVED` 상태로 복원한다.
- 이 방식으로 도메인 객체 변경을 최소화한다.

### 4. 계층 분리
- `persistence/db`: JDBC 연결, 설정, 스키마 초기화
- `persistence/repository`: 상영 정보 및 예매 정보 저장/조회
- `persistence/seed`: 기본 상영 데이터와 고정 좌석 배치
- `persistence/CinemaDatabase`: 애플리케이션이 사용하는 DB 진입점

### 5. 구현 순서
1. JDBC 연결 및 트랜잭션 유틸을 만든다.
2. H2 스키마 초기화를 구현한다.
3. 기본 상영 데이터와 고정 좌석 배치를 만든다.
4. 상영 정보를 저장/조회하는 repository를 구현한다.
5. 예매 정보를 저장/조회하는 repository를 구현한다.
6. `Main`에서 데이터베이스를 통해 상영 정보를 로드하고 예매를 저장하도록 연결한다.
7. 데이터베이스 연동 테스트를 작성한다.

### 6. 식별자 전략
- ID는 문자열 기반으로 관리한다.
- 의미 있는 식별자를 사용한다.
- 예:
  - 영화: `movie-f1`
  - 상영관: `screen-1`
  - 상영: `screening-movie-f1-screen-1-2025-09-20T10:20`
  - 예매: `reservation-screening-...-A1`

# 4 단계 - 영화 예매(프레임워크)

## HTTP API 기능 목록
- [x] `GET /api/movies`로 영화 목록과 상영 정보를 JSON으로 조회한다.
- [x] `POST /api/reservations`로 여러 상영의 좌석 예매를 생성한다.
- [x] 결제 포인트와 결제 수단을 반영해 총 결제 금액을 계산한다.
- [x] 존재하지 않는 상영, 이미 예약된 좌석, 잘못된 요청 형식에 대해 적절한 오류 응답을 반환한다.
- [x] HTTP API 테스트를 작성한다.

## 구현 전략

### 1. 진입점 분리
- 콘솔 실행용 `Main.kt`는 유지한다.
- HTTP 서버용 Spring Boot 진입점을 별도로 추가한다.
- 콘솔과 HTTP는 서로를 호출하지 않고 같은 도메인과 영속 계층을 재사용한다.

### 2. 계층 분리
- `api`: HTTP 요청과 응답, 예외 처리만 담당한다.
- `application`: 요청을 도메인 조합으로 연결하는 유스케이스를 담당한다.
- `domain`: 기존 비즈니스 규칙을 유지한다.
- `persistence`: DB 로드와 저장을 담당한다.

### 3. 도메인 변경 최소화
- 기존 `MovieTheater`, `Cart`, `Receipt` 중심의 흐름을 유지한다.
- HTTP에서 필요한 식별자 계산은 별도 유틸로 분리해 도메인 변경을 줄인다.
- 각 요청마다 DB에서 최신 영화관 정보를 다시 로드해 좌석 상태를 검증한다.

### 4. 예매 처리 방식
- 요청의 `screeningId`를 실제 상영 도메인으로 매핑한다.
- 좌석 문자열을 `SeatCoordinate`로 변환한 뒤 기존 좌석 검증 로직을 사용한다.
- 장바구니를 구성한 뒤 영수증을 발급하고 포인트와 결제 수단을 순서대로 적용한다.
- 결제 확정 이후에만 예매 정보를 저장한다.

### 5. 오류 응답 전략
- 잘못된 요청 데이터는 `400 Bad Request`를 반환한다.
- 존재하지 않는 상영은 `404 Not Found`를 반환한다.
- 이미 예약된 좌석이나 시간 중복 예매는 `409 Conflict`를 반환한다.
- 오류 본문은 `{ "message": "..." }` 형식으로 통일한다.

### 6. 테스트 전략
- HTTP 계층 테스트는 상태 코드, JSON 구조, 본문 값을 검증한다.
- 핵심 비즈니스 규칙은 기존 도메인 테스트가 계속 담당한다.
- API 테스트에서는 정상 흐름과 예외 흐름을 모두 확인한다.
